# 一篇文章，如何高质量分发三平台

多平台分发最浪费时间的，往往不是写作，而是反复复制、清理格式、补字段，最后还要逐个确认“到底有没有保存成功”。真正可靠的工具，不该只是替你打开三个网页，而应该把一份源稿变成三份可继续编辑、可核验的草稿。

## 同一篇文章，不等于三次粘贴

三个平台面对的读者和编辑器不同，内容结构也不同：

| 平台       | 更适合的正文                | 发布前重点               |
| ---------- | --------------------------- | ------------------------ |
| 小红书     | 干净、易扫读的纯文本        | 标题节奏、段落长度、配图 |
| 掘金       | 保留层级与代码块的 Markdown | 分类、标签、技术细节     |
| 微信公众号 | 稳定的富文本 HTML           | 摘要、封面、移动端排版   |

如果把同一份 Markdown 原样粘贴三遍，表面上节省了几分钟，实际上把格式错乱、字段遗漏和误发风险留到了最后。

## 一套可验证的四步工作流

### 1. 保留唯一源稿

标题、正文和元数据只维护一份。后续修改先回到源稿，不在三个平台上各改一套“最终版”。这样可以避免内容分叉，也能清楚回答：哪一份才是最新内容？

### 2. 自动生成平台变体

转换不是简单去掉符号，而是保留信息结构：

- 小红书版本移除 Markdown 标记，保留标题、段落、列表和代码含义；
- 掘金版本保留 Markdown，避免技术文章在复制时丢失代码块；
- 公众号版本生成富文本 HTML，让标题层级、引用和表格可直接预览。

### 3. 发布前做结构化预检

预检应该把“阻断项”和“建议项”分开。标题为空属于阻断项；小红书缺少配图、掘金缺少标签则属于建议项。两者混在一起，只会让用户在一堆警告里找不到真正需要处理的问题。

### 4. 以草稿为交付结果

自动化完成后，至少要留下三个可回查的结果：平台名称、草稿状态、草稿地址。只有看到服务端草稿存在，才能说明任务成功；“页面已经打开”或“输入框看起来有内容”都不够。

```ts
type DraftResult = {
  platform: 'xiaohongshu' | 'juejin' | 'wechat'
  status: 'saved' | 'login-required' | 'failed'
  draftUrl?: string
}
```

## 我会保留的五个产品细节

第一，批量任务必须允许单个平台重试。某个平台登录失效，不应迫使另外两个已经成功的平台重新执行。

第二，主操作始终固定可见。长配置区可以滚动，但“准备草稿”不能被推到屏幕之外。

第三，平台设置按任务拆分。分类、标签和摘要属于内容设置；账号或接口属于连接设置，不应该全部挤在同一个长表单里。

第四，成功状态要诚实。“已填入编辑器”“已保存草稿”“已发布”是三个不同阶段，界面文案必须准确。

第五，登录态应该保存在本机的隔离会话中。文章和会话不经过额外中转服务，既减少配置，也缩小数据暴露范围。

## 发布前的最后检查

- 标题在三个平台都没有被截断；
- 首段可以独立作为摘要，不依赖上文；
- 列表、引用、表格和代码块仍然可读；
- 小红书段落足够短，并预留配图位置；
- 掘金分类与标签已补齐；
- 公众号封面和移动端预览已检查；
- 三个平台的草稿列表都能找到本次文章。

> 好的分发工具不是替人做最后一次冒险点击，而是把重复劳动自动化，把关键判断留给人，并为每一步提供可验证的结果。

当“写作、适配、预检、保存、回查”形成闭环，多平台发布才真正从一次性的复制劳动，变成可以稳定复用的内容工作流。
